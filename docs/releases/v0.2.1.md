# Engineering Ownership v0.2.1

This release rewrites the shipped evaluation manifest. No runtime behaviour
changes: the CLI, the skill router, and the hooks are untouched.

## Why the version moved

`evals.json` ships inside the release package, and this project publishes the
claim that a rebuilt release archive matches its published digest. Editing the
manifest under the `0.2.0` label would have made that claim quietly false. The
`0.2.0` artifact and its digest are unchanged, and the digest is now recorded in
`docs/releases/v0.2.0.md` so it survives independently of the untracked build
directory.

## Evaluation manifest

The previous manifest could not measure what it claimed to. An audit of its 32
expectations found three that a competent engineer unfamiliar with this skill
could pass on merit. The rest required vocabulary only this skill supplies, were
satisfied by a response that said nothing, bundled independently observable
things into one verdict, or scored a response worse for having fixed the problem
it was asked about.

The manifest is rewritten around four rules, now enforced by
`tests/test_evals.py`:

1. An expectation must be passable on merit, so it may not require this skill's
   private vocabulary - including its risk-tier labels.
2. An expectation may not be satisfied by silence. Restraint is measured by
   requiring the response to show it considered the question and chose.
3. An expectation describes one observable behaviour.
4. An expectation may not penalise a response for resolving the problem.

Expectations that duplicated what `tests/` already asserts deterministically
were removed. Conformance belongs to the unit tests; the evaluation measures
efficacy.

## What is new

- **A ninth scenario**, `change-that-contradicts-an-accepted-decision`. The skill
  requires an agent to record whether a change follows, replaces, or invalidates
  an earlier decision, and never to overwrite accepted rationale silently. That
  is the most maintenance-specific behaviour it asks for, and nothing tested it.
- **Prompts are product-neutral.** Several named this project or its concepts,
  which made those scenarios unanswerable for a baseline regardless of how the
  expectations were worded.
- **Fixtures can start from a settled state**, so a scenario can present an
  accepted decision that is already implemented rather than only planned.

## Still open

No efficacy number is published. The rewritten expectations have not yet been
run at a sample size that would support one, and
`docs/validation/skill-evaluation.md` records what remains before one can be.
