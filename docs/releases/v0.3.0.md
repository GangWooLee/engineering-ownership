# Engineering Ownership v0.3.0

This release rewrites the shipped evaluation manifest, rewrites the skill's
selection-time description, adds a terminal close state to change records, and
removes the write-only competency tag subsystem. It is a minor version, not a
patch: the CLI gains `change close` and loses `--competency`, `status` and the
bare `handoff` become open-work views, and the hooks stop counting closed
records as stale. The work was staged under a `0.2.1` label while unreleased;
the label moved to `0.3.0` once it carried a breaking change, and no `0.2.1`
was ever tagged or published.

## Description rewrite

The description is the only text a model reads when deciding whether to
consult the skill. Measured against frozen trigger probes with pre-registered
bars, the old description engaged in zero of seven runs on a repository
without this workflow's config; the rewritten one engaged on sixteen of
seventeen should-trigger probes and zero of twelve should-not probes, with a
held-out probe half consistent. `triggers.json` ships in the package as
documentation of intended triggering.

## Terminal close state

`engineering change close <id>` records the closing timestamp and HEAD
revision. Closed records leave plain `status`, the repo-wide `handoff`, and
the session reminder, but stay on disk and readable (`status --all`,
`handoff --change`, `explain`, `refs check`). Continuation after close is a
new change record; there is no reopen and no gate on closing. This replaces
the hand-written `Status:` line convention in Briefs.

## Contract-declared reference exclusions

`refs check` scanned every text file in the repository, so worked examples in
tutorials and synthetic markers in evaluation fixtures registered as dangling
decision references — a gate that is permanently red teaches people to ignore
it. The contract now accepts an optional `refs.exclude` array of
repository-relative globs, validated like every other contract path, and both
`refs check` and the `check` gate filter scanned paths through it. Each
repository declares its own illustrative paths in a reviewed file; nothing is
hard-coded in the shipped CLI.

## Removed: competency tags

The eight tags were written once and read by nothing except two verbatim
echo lines. The set, the `--competency` flag, the catalog resource, the echo
sites, the schema requirement, and the reference doc are removed. Evidence
records that carry a legacy `competencies` array remain fully readable.

## Why the version moved

`evals.json` ships inside the release package, and this project publishes the
claim that a rebuilt release archive matches its published digest. Editing the
manifest under the `0.2.0` label would have made that claim quietly false. The
`0.2.0` artifact and its digest are unchanged, and the digest is now recorded in
`docs/releases/v0.2.0.md` so it survives independently of the untracked build
directory.

## Evaluation manifest

The previous manifest could not measure what it claimed to. An audit of its 32
expectations found three that a competent engineer unfamiliar with this skill
could pass on merit. The rest required vocabulary only this skill supplies, were
satisfied by a response that said nothing, bundled independently observable
things into one verdict, or scored a response worse for having fixed the problem
it was asked about.

The manifest is rewritten around four rules, now enforced by
`tests/test_evals.py`:

1. An expectation must be passable on merit, so it may not require this skill's
   private vocabulary - including its risk-tier labels.
2. An expectation may not be satisfied by silence. Restraint is measured by
   requiring the response to show it considered the question and chose.
3. An expectation describes one observable behaviour.
4. An expectation may not penalise a response for resolving the problem.

Expectations that duplicated what `tests/` already asserts deterministically
were removed. Conformance belongs to the unit tests; the evaluation measures
efficacy.

## What is new

- **A ninth scenario**, `change-that-contradicts-an-accepted-decision`. The skill
  requires an agent to record whether a change follows, replaces, or invalidates
  an earlier decision, and never to overwrite accepted rationale silently. That
  is the most maintenance-specific behaviour it asks for, and nothing tested it.
- **Prompts are product-neutral.** Several named this project or its concepts,
  which made those scenarios unanswerable for a baseline regardless of how the
  expectations were worded.
- **Fixtures can start from a settled state**, so a scenario can present an
  accepted decision that is already implemented rather than only planned.

## Still open

No efficacy number is published. The rewritten expectations have not yet been
run at a sample size that would support one, and
`docs/validation/skill-evaluation.md` records what remains before one can be.
